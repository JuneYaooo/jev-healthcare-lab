# 逐任务多问题与并发测试协议

[返回首页](../README.md) · [任务目录与结果](tasks/README.md) · [原始档案](../results/task-performance-v1/README.md)

性能结果与准确率一起按临床任务展示在首页各场景表和任务详情页。测试单位是临床任务族：病例诊断的两个来源仍合并，不因来源拆分重复计权。当前测试 JEV 1.13 与 DeepSeek V4.1 Flash，其他三模型保留原单题结果，本轮没有它们的多题与并发成绩。

## 原题、金标与分组

从原临床范围的 1,514 道题中，在每个任务内按 SHA256(固定种子,题号) 排序，选前 min(32,题数) 道，合计 566 道。覆盖 26 个有题任务，3 个空任务不调用 API。所有模式、两个模型、三轮重复使用相同题目面板，不按模型准确率或速度挑题。原有完整临床准确率继续使用全量题目；本轮子集准确率不回填全量榜单。

题目沿用原 state、问题、候选和金标。取样包含非商业附加来源，分发与用途继续遵循每条 provenance 的原许可，不能把整体视作无限制商用数据。小样本任务不复制题目凑并发；三次重复也不增加独立病例数。

多问题指**同任务多道原题一起判断**：把各原题的完整 state 嵌套到 `state.records.qNNN`，为每条记录保留原问题与候选，增加“只依据对应记录作答”的定位说明。每条输出映射回原题号与原始金标。它不是“同一患者新增多个判断维度”，也不生成新的临床答案。不同病例放在同一上下文可能产生干扰，准确率与完整率正是需要同时测量的指标。

## 每个任务的测试矩阵

| 模式 | 每请求题数 | 同时请求数 | 工作量 |
| --- | --- | --- | --- |
| 逐题基线 | 1 | 1 | 同一组最多 32 道题 |
| 逐题并发 | 1 | min(8,N)、min(32,N) | 同上 |
| 多题打包 | 目标 min(8,N)、min(32,N) | 1 | 同上，全部题目恰好出现一次 |

N 为该任务实际取样题数，重复档位去重。每种模式、每模型三轮，共 708 个正式单元、10,656 次正式请求；另记录接口检查和预热，不计入任务成绩。批量与并发分别改变，避免把每包题数和同时请求数当成同一个参数。首页多题表使用同一子集的逐题基线与最大打包档配对展示准确率和整组耗时，并发表使用同一子集，配对展示依次提问（并发 1）与同时提问（最高并发档）的准确率和整组耗时；未按结果挑选“最快档”，任务详情保留全部档位。

若材料过长，按原顺序贪心拆包：序列化 state 加最长问题不超过 31,000 UTF-8 字节，整个 request 不超过 63,000 字节。这是保守预检边界，不是假称精确 tokenizer 计数。不会截断材料、丢弃题目或用短题替换长题；两模型使用相同分包。比如目标 32 问可能实际拆成多个请求，页面展示实际题数范围，整组耗时包括全部分包。

每档并发最多等于实际独立题数。最高档常只有一波请求，因此本轮衡量有限批次完成效率，不是持续吞吐上限；不能用它确定服务容量或生产限流参数。

## 接口、连接与计时

单题请求完全复用原临床测试提示与格式。多题时 Jev 使用原生 questions；Flash 使用 JSON object 模式，输出精简映射 `{"q000":"选项键","q001":"选项键"}`，不要求额外解释或自报概率。必须返回原选项键，不能把 opa 转成 A 或把候选文本当作键。Flash 关闭思考、temperature=0，多题输出上限 max(512,40×问题数)。请求只包含材料、问题与候选，gold、来源、任务统计及历史答案不发送。

每模型使用最多 32 个持久线程，线程内持有独立 HTTP/1.1 Session。正式测量前每个线程发送一道非临床颜色选择题，预热记录保存；会话跨测试单元复用。两个模型顺序运行，单元顺序在调用前按固定种子随机化，每单元之间间隔 0.15 秒。连接仍可能被服务商关闭或受网络影响，不能把全部延迟归因于模型计算。

自动重试为零。连接超时 10 秒，读取空闲超时 60 秒；这不是严格的请求总时长上限。超时、连接错误、HTTP 错误与无效输出保留，401/402/403 停止运行。服务商缓存不受控，重复题可能命中缓存，usage 原样保留，不宣称冷缓存测量。接口预检同样可能影响缓存。

每条请求的耗时从线程开始处理题包到全部结果读完、解析及验证结束，包含序列化和网络，队列等待单独记录。整组墙钟从释放工作线程到本组所有请求结束，含排队与失败拖尾，不含归档磁盘写入。不以首 token 时间代替完整结果，不把多题耗时除以题数后标成完整请求时间。

## 准确率、完整率与费用

- 逐项准确率：正确决策数除以全部预定决策数，失败、缺失和非法选项计错。
- 有效决策吞吐与正确决策吞吐：三轮相应决策总数除以三轮整组墙钟总和。
- 完整包：全部预定题号都存在，值为合法选项，且没有额外键。只返回部分合法结果的请求仍列为不完整；合法条目可单独计数。截断、不可解析或重复键的 JSON 整包计无效，不事后修复。
- 页面展示三轮整组耗时均值与范围、完整包数、失败数及原始记录。少于 20 次请求不展示请求 P95，重复题不构成独立准确率样本。
- 费用按冻结的 2026-10-12 官方价目和实际 usage 估算。Flash 分缓存命中、未命中与输出，列闲时到高峰上下界；Jev 输出免费。失败缺用量时不填完整单位成本。预热费用另保留 usage，不算任务决策单价，表内费用不是账单。

## 复现与审计

```bash
python3 -m pip install -r requirements-performance.txt
python3 -m unittest discover -s tests -p 'test_task_performance*.py'
# API 调用会产生费用；需 TYPESAFE_API_KEY、DEEPSEEK_API_KEY。
# 输出目录必须不存在，不把中断的时间片拼成一个批次。
python3 scripts/run_task_performance.py run --output work/task-performance-new-run
# 以下均离线，不调用 API。
python3 scripts/build_task_performance_report.py --check
python3 scripts/generate_catalog_docs.py --check
```

数据清单、原题子集、题包到原题的映射、执行顺序、当时代码、原始响应与时间均归档。复核器从原始响应重算每个任务每个档位，检查矩阵完整性、输入哈希、原金标、拆包无遗漏和计时一致性。查看结果时直接进入[相应任务](tasks/README.md)，无需从全局混合吞吐推测某个任务的表现。

此前的[混合任务与合成看板实验](PERFORMANCE_RESULTS.md)保留为历史记录，不分摊到医疗任务。当前协议另保存了[初次接口检查](../results/task-performance-interface-check/README.md)及[扁平输出检查](../results/task-performance-interface-check-flat/README.md)：最初的多题提示要求嵌套 choice 对象，但 Flash 返回题号到键的扁平 JSON；正式协议在冻结前改为明确要求精简扁平映射，并重新检查。预检结果不混入正式成绩。
