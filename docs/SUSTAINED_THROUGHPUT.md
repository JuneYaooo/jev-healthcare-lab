# 持续多题并发测试协议

测试目标是比较医疗判断服务在持续负载下的准确率、吞吐、延迟与费用。旧测试把多题与并发分开，且只处理有限的一批题，不能据此判断持续服务能力。

## 负载与数据

本轮先测病例并发症、用药方案、病例诊断、中医证型四个任务。每个任务沿用冻结数据中的 32 道原题及原始金标，分成每请求 8 题的四包，循环发送。重复发送用于施加负载，不增加独立医学样本数。

- 每请求 8 题 × 8、32、64 个并发工作器，两个模型使用相同请求内容与金标。
- 每个工作器收到完整响应后立即补入下一包，持续运行；不是只发送一波并发请求。
- 每档先预热 5 秒，再统计连续 30 秒，重复两轮。各任务顺序按固定种子打乱，模型顺序交替。两模型不同时施压，避免共享客户端资源。
- 另测每请求 200 题 × 8、32 并发的确定性规则分流板。三块固定分流板循环发送，只有工程吞吐意义，不作为医学能力证据。它们包含多条记录及共享规则，并非同一份病历上的 200 项医学金标判断。
- 医疗数据同样是多病例拼包。针对“同一份病历读取一次、同时回答许多不同问题”的临床收益，仍需另建有专家金标的多字段病历数据集。

默认矩阵共 56 档。每档完成后保留全部原始响应、时间戳、用量、错误及每 5 秒的吞吐。Flash 关闭思考，返回紧凑 JSON 选项键；不修复答案、不放宽金标、不丢弃失败请求。JEV 使用原生多问题接口。

## 指标

**每秒返回的合法判断数** = 统计窗口内完整响应中合法选项数 ÷ 30 秒。部分响应中的合法项可以计入，但完整包率另列。答错的合法选项仍属于处理能力；同时记录每秒正确判断数，避免将速度等同于质量。

预热时发出、窗口内完成的请求计入吞吐；窗口后才返回的请求保留但不计入窗口吞吐。这样不会把尾部等待时间排除后虚增吞吐。

准确率、响应延迟、完整包率及成本使用窗口内发出的请求，并等待它们完成或超时。准确率先分别计算各固定包的重复平均分，再按原题数汇总，避免较快的包被多次采样而占更高权重。原题仅 32 道，不以重放次数计算医学置信区间。每千次正确判断成本按实际发出请求的总费用与答对数计算，包含答错的费用。

P95 延迟是收到并校验完整响应的时间，不是首字时间；另存包含配额排队的端到端 P95。请求总超时设为 30 秒，连接建立另设 10 秒上限，均纳入失败与延迟统计。任一请求缺少用量，该档单位成本标记为待核算；已知用量费用仍保留。Flash 费用区间按缓存命中、未命中、输出用量及冻结的闲时／高峰价格分别计算。重复材料可能命中缓存，本轮不声称是冷缓存。

## 并发与配额

配置并发是工作器数，实际在途 HTTP 并发可能更低，报告同时给出均值和峰值。客户端使用异步 HTTP、每模型独立复用连接池（128 连接、闲置复用 15 秒），保留事件循环延迟，用于发现客户端阻塞。

正式测试先通过系统解析器取得各 API 域名的地址，整轮复用，域名与 TLS 校验保持正常；DNS 查询时间单独归档，不计入接口吞吐。首次环境预跑发现本机解析 JEV 域名约需 30 秒，已中断并保留 [异常记录](../results/sustained-throughput-dns-pilot/README.md)。复跑使用相同矩阵与金标，两模型执行同一 DNS 预解析规则。此设置不代表包含冷启动 DNS 的真实用户首次请求。

2026-10-12 查阅 [JEV 模型文档](https://docs.typesafe.ai/models)：JEV 1.13 公布 80 请求／秒、100K 输入 token／秒配额。客户端分别以 76 请求／秒、95K 输入 token／秒平滑发出请求；先逐包校准输入用量，再加 10% 估算余量。配额等待时间单独保留。配额不是模型的计算上限；自定义或企业配额可能不同。

同日 [DeepSeek 限流文档](https://api-docs.deepseek.com/quick_start/rate_limit/) 列出 Flash 2,500 并发限制，本轮最高 64 并发低于此值。429、503、529 按服务端提示退避；不重试原请求，不轮换密钥。最近 20 个响应中至少 10 个请求错误／超时会中止该任务该模型的后续档位，保留触发中止的窗口与跳过记录。汇总仅使用完整运行且未触发中止的窗口；若错误阈值在收尾阶段触发，该档也不纳入汇总，并记录触发阶段。这不表示该档的 30 秒观察时间一定未走完。

预算是已知用量的高峰价估计达到 $25 后不启动下一档，并非在途请求的硬性消费上限。每档最多 5,000 次请求。鉴权或请求配置错误中止整轮。

## 结论边界

本轮是有配额约束的闭环短时持续负载测试。它能回答这些固定任务在这些设置下每秒完成多少判断、准确率是否变化、完整结果等待多久及费用多少。只有两轮 30 秒，不能推出全天稳定性、开放流量下的 SLA 或服务端最大吞吐。

如果吞吐随并发上升而增长，只能说尚未测到上限；如果先碰到账号配额，应报告配额约束下的结果。不得从非医疗分流板的高吞吐推断医疗判断质量。

## 复现

需要 Python 3.11 或更新版本。

```bash
python -m pip install -r requirements-throughput.txt
python -m unittest discover -s tests -p 'test_sustained_throughput.py'
python scripts/run_sustained_throughput.py --output results/sustained-throughput-new
```

接口检查可加 `--smoke`；扩展任务可使用 `--all-tasks` 或 `--families`。输出目录必须不存在，避免覆盖历史记录。认证沿用本地 `.env`，原始结果不保存请求头或密钥。

## 后续数据缺口

持续施压本身不需要另造医学题，现有冻结题可循环使用；但它只能支持该固定题组、包含缓存影响的性能结论。若要比较缓存较少的业务流量，需要扩大不同材料的覆盖，并单独报告缓存命中比例。

验证同病历多字段判断则需要新增数据：每份病历对应多项独立问题，保留各字段的候选、标准答案及证据位置，覆盖明确存在、明确不存在和材料不足三种情况。应由有依据的原始标注或专家复核提供金标，不能把模型生成答案当作临床真值。问题数与病例数分别计数，并在同一病例上测试不同字段数量与并发档位。

当前 200 题规则板适合检验接口完整性和输出耗时，不能替代上述多字段医学标注。

本轮使用 Choice 选择题，不评估 Score 等其他输出类型或概率校准质量；格式有效、选项答对与概率校准是不同指标。
